# Goal 产品方案

状态：待评审；基于 `test` 分支 `0483924`。本文描述拟实现的行为。

## 1. 产品目标

用户给 Agent 一个目标，OpenSpace 在后台持续推进，直到完成验收、需要用户输入、用户暂停/取消，或执行额度用尽。关闭页面不影响执行；重新打开能看到当前进度与停止原因。

典型输入：

```text
@开发 /goal 给登录页增加验证码，完成实现并运行相关测试
```

系统立即创建 Goal 卡片和专属线程，Agent 调查现状、明确验收项、执行和验证。一次回复结束但目标未完成时，系统自动安排下一轮。

Goal 与项目设置中的 `project.goal` 分开：前者是有负责人、执行历史和生命周期的具体任务；后者仍是项目背景。既有 Task、Workflow 不自动转换成 Goal。

## 2. 首版范围与默认值

首版由一个 Agent 负责一个 Goal；保留现有代码编辑、工具、流式回复、审批和提问能力。支持创建、状态查询、补充要求、暂停、恢复、取消与完成证据展示。

先为 Codex runtime 开启 Goal；这是交付范围选择，采用 OpenSpace 自己的调度器，不依赖运行时是否提供原生 `/goal`。其他 runtime 接入前需验证会话恢复、结构化结果与中断行为。

首版不提供自动多 Agent 分工、定时执行、后台自动重试部署，或跨 Goal 并行编辑隔离。相同 workspace 默认最多一个执行中的 Goal；其他 Goal 排队。普通聊天和既有 Workflow 仍可能编辑同一 workspace，首版展示此并发限制，独立 worktree 属后续阶段。

默认执行额度建议为 **20 轮、60 分钟累计运行时间**，先达到者暂停。两者包含规划、执行、验证和失败重试；排队、暂停、等待用户的时间不计入。显示“轮次/运行时间”，不显示缺乏准确统计的费用或 token 预算。管理员可配置更低上限，用户恢复时可明确增加额度。

## 3. 输入与命令

| 输入 | 产品行为 |
| --- | --- |
| `/goal <目标>` | 唯一可用 Agent 时直接创建；多个 Agent 时打开负责人选择；没有可用 Agent 时提示添加 |
| `@agent /goal <目标>` | 指定负责人并创建 |
| `/goal <目标> @agent` | 仅末尾独立 mention 用作负责人；从目标文本移除该 mention |
| `/goal`、`@agent /goal` | 打开创建表单，不创建空目标，不唤醒普通聊天 |
| `@all /goal ...`、多个负责人 | 提示首版只支持一个负责人，不启动任何 Agent |
| `/goal-status [id]` | 显示当前线程的 Goal 或指定 Goal |
| `/goal-pause [id]` | 暂停自动执行，并中断正在运行的一轮 |
| `/goal-resume [id]` | 恢复可恢复的 Goal；额度用尽时先在卡片中增加额度 |
| `/goal-cancel [id]` | 终止 Goal；已产生的文件修改保留 |
| `/goal-update [id] <补充要求>` | 追加要求，触发按新要求重新规划；不能修改已完成或取消的 Goal |

`/goal-*` 用独立命令名，避免把“pause 数据同步任务”这样的目标误识别为控制操作。线程内省略 id 指向该线程 Goal；主频道省略 id 时，只有一个未终止 Goal 才自动选择，否则展示选择器。恢复已失败 Goal 必须给出纠正信息；已完成、已取消 Goal 需创建新 Goal。

只有消息开头的命令或“开头的单个 mention + 命令”才启用 Goal。`帮我解释 /goal`、代码块和引用里的 `/goal` 保持普通文本。负责人的解析不能把目标描述中任意 `@xxx` 当成执行对象。

创建表单包含：目标、负责人、可选验收标准、额度。目标明确且负责人唯一时直接启动；必填条件缺失时再补充。没有额外的固定“批准计划”关卡；运行时权限审批继续沿用现有机制。

新命令属于内置保留命令。若现有 Workflow 已用同名 trigger，升级时保留数据、标记冲突并提示更名；不得静默改变该 Workflow 的触发行为。在冲突解决前，聊天命令明确提示冲突，仍允许从 Goal 创建表单启动。

## 4. 执行与完成

1. 创建：保存原始目标与用户明确提供的验收条件；展示负责人、额度和线程入口。
2. 调查与计划：Agent 读取必要上下文，把目标拆成少量验收项，展示当前步骤。原始要求保持可追溯；Agent 增补的假设与验收项单独标记。
3. 执行：每轮产生可见进展；未完成则继续下一轮。内部调度提示不刷到聊天主线。
4. 验证：Agent 声称完成后，安排单独的验证轮，逐项对照当前版本要求，提供测试结果、文件或其他产物证据。
5. 完成：验收项全部通过才标记完成。只有回复“完成了”或一轮执行成功不足以完成 Goal。缺少可执行验证的任务，可提供文档/产物对照；证据缺失则继续或等待用户。

验证轮首版仍由同一个 Agent 完成，不等同于独立人工审查。展示“Agent 已验证”以及每项证据，避免暗示平台保证代码正确。用户明确要求人工验收时，Goal 等待用户确认后才完成。

连续三轮没有新增产物、验收进展或有效的新调查证据，暂停并展示“未取得进展”。首版进展判断包括 Agent 报告与可观察执行记录，不只比较回复文本长度；重复工具调用或改写计划不算进展。

## 5. 状态与用户干预

| 状态 | UI 文案与行为 |
| --- | --- |
| queued | 排队中；可暂停、取消 |
| running | 执行中；显示当前步骤、已完成验收项与运行时间 |
| verifying | 验证中；显示验收项及证据 |
| awaiting_input | 等待你补充信息；提供输入入口 |
| awaiting_approval | 等待权限审批；复用审批卡片 |
| pausing | 正在暂停；停止后续调度，等待本轮退出 |
| paused | 已暂停；显示手动暂停、额度用尽、无进展或重启中断的原因 |
| cancelling | 正在取消；等待本轮退出 |
| completed | 已完成；展示成果、验收证据和剩余限制 |
| cancelled | 已取消；保留执行记录和已修改文件 |
| failed | 执行失败；展示错误与纠正后恢复入口 |

Goal 线程中用户发送普通消息，视为补充要求，不自动开启独立的普通 Agent run。平台使旧轮次失效、中断旧轮次，再基于新要求继续；纯旁注可使用既有 `/comment`。等待运行时问题时，优先通过问题卡片作答；普通线程补充要求采用中断重规划路径。

频道主线的普通 @ 消息保持聊天语义。如果会中断同 Agent 的 Goal，先将该 Goal 暂停并展示原因；不能让 Goal 调度器立即把它重新启动。频道“停止所有 Agent”同时暂停频道全部未终止 Goal，包括排队中的 Goal。

暂停/取消表示停止继续执行，不承诺回滚文件，也不保证撤回已发出的外部操作。界面直接显示“已产生的修改会保留”。

## 6. 界面

- 输入框提示列出 Goal 命令，兼容 `@agent /go` 的补全；本地记忆的默认 mention 不能覆盖用户显式选择的负责人。
- 主频道显示一个 Goal 卡片：目标、负责人、状态、当前步骤、验收进度、轮次与运行时间、暂停/继续/取消按钮。
- 所有执行和验证回复进入专属线程。在线程里创建 Goal 时沿用当前线程；首版每个线程最多一个未终止 Goal。
- 详情展示原始要求、补充要求、计划、验收项、证据、执行记录和停止原因；移动端复用现有侧栏容器。
- 刷新/重连后从服务端重新获取状态，不能只依赖 WebSocket 增量。

## 7. 权限与验收

有频道访问权限的用户可查看和创建 Goal；创建者或有频道管理权限的用户可控制 Goal。所有操作重新验证频道权限和当前成员关系，运行时审批沿用现有审批权限。权限移除或负责人移出频道会暂停 Goal。

首版交付验收：两种创建入口等价；一轮未完成能自动继续；已完成不再调度；暂停后无新工具启动；额度在单轮内也生效；补充要求覆盖旧轮次结果；断网刷新可恢复界面；服务重启不重复执行不确定的旧轮次；重复发送不重复创建；完成卡片能追溯每项验收证据。

具体实现、竞态和测试见 [Goal 技术方案](goal-technical-design.md)。
