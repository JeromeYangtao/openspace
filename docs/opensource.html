OpenSpace Open Source Readiness

把 OpenSpace 开源成一个可被理解、可被运行、可被共建的项目

开源不是简单把仓库设为 public，而是让第一次看到项目的人能快速判断价值、跑起来、理解边界，并知道如何安全地贡献。

本地优先 可复现启动 文档可信 贡献低摩擦 数据安全
1

产品目标

清晰传达 OpenSpace 是 Programmable AI Team OS：用户设定 Goal，系统组织 AI Team、Workflow 和知识沉淀，而不是另一个普通聊天壳。

2

工程目标

让开发者可以在干净环境中完成 pnpm install、pnpm dev、打开项目、发送第一条 @ 消息的完整链路。

3

社区目标

建立 issue、PR、路线图和行为规则，让外部贡献集中在 bug 修复、runtime adapter、workflow 模板和文档改进上。

开源前准备清单

仓库与代码卫生

  • 确认仓库中没有密钥、token、个人路径、私有域名或真实用户数据。
  • 检查 .gitignore 覆盖 .env、SQLite 数据库、日志、构建产物和本地缓存。
  • 跑通 pnpm typecheck、pnpm lint、pnpm build，并记录已知失败项。
  • 删除或标注实验性 spike 中不应被用户依赖的脚本。
  • 确认默认配置只监听本地地址，避免首次运行暴露到公网。

文档与上手路径

  • 更新 README 的一句话定位、截图、快速开始、常用命令和排障入口。
  • 补齐 CONTRIBUTING.md、CODE_OF_CONDUCT.md、SECURITY.md。
  • 明确 Node.js、pnpm、Codex CLI、Cursor CLI / SDK 的版本要求。
  • 提供最小 smoke test：从 Welcome 页打开 workspace，到 #general 发送第一条消息。
  • 把产品边界写清楚：单用户、本地工具、非企业权限系统、非托管 Agent 市场。

许可证与治理

  • 确认 LICENSE 与项目商业化预期一致，并在 README 中声明。
  • 定义 maintainers、review 规则、版本发布节奏和 issue triage 标签。
  • 准备 GitHub issue templates：Bug、Feature、Runtime Adapter、Docs。
  • 准备 PR template：变更说明、测试结果、截图或录屏、兼容性影响。
  • 给重大设计变更设定 RFC / discussion 流程，避免路线图被随机 PR 拉偏。

安全与隐私

  • 说明数据落在 <workspace>/.openspace/ 与 ~/.openspace/projects.json 的边界。
  • 明确哪些文件建议入仓，哪些文件必须保持本地，例如 openspace.db。
  • 为 CLI runtime 调用外部模型 API 的行为写出透明说明。
  • 添加漏洞报告方式和不公开披露窗口。
  • 检查日志中不会默认写入 prompt、secret、完整本地路径或敏感输出。

极简部署方案：install.sh

OpenSpace 开源后的主安装路径采用宿主机 scripts/install.sh，目标是一行命令完成拉取、安装依赖、构建和 PM2 常驻启动，同时复用用户本机已登录的 codex / cursor-agent。

  • 推荐命令：curl -fsSL https://raw.githubusercontent.com/jeromeyangtao/openspace/main/scripts/install.sh | bash
  • 应用目录：~/.openspace/app
  • 数据目录：~/.openspace
  • 访问地址：http://127.0.0.1:4179
  • 管理命令：pm2 logs openspace、pm2 restart openspace --update-env、pm2 stop openspace

建议发布节奏

  1. Internal Review：完成安全扫描、文档校对、最小启动链路验证。
  2. Soft Launch：先邀请少量开发者试跑，收集安装、概念理解和 runtime 配置问题。
  3. Public Launch：仓库公开，同步发布 README、路线图、贡献指南和首批 good first issues。
  4. Post Launch：48 小时内集中处理安装问题，第一周后整理 FAQ 和下一版计划。

首批共建方向

  • Runtime adapters：Claude、Kimi、Copilot、Gemini 等 CLI / SDK 适配。
  • Workflow templates：feature、bugfix、research 之外的真实团队流程。
  • Onboarding polish：错误提示、空状态、首次运行排障和配置检测。
  • Docs and examples：真实项目 walkthrough、截图、架构图和常见问题。

GitHub 发布镜像

公司 GitLab 继续作为日常开发主仓库，GitHub 只承载开源发布结果。公开发布时使用 scripts/publish-github.sh 从内部 main 生成本地 public-main squashed snapshot，再推送到 git@github.com:JeromeYangtao/openspace.git 的 main 分支。

  • 日常 commit、实验分支和内部历史只保留在 GitLab。
  • 发布前必须保证工作区干净，并完成密钥、私有域名、内部数据检查。
  • GitHub 只接收整理后的公开 release commit，避免暴露内部提交历史。

一句话原则

开源版本的目标不是展示所有想象力，而是让用户相信：这个项目能跑、边界清楚、值得参与，并且会沿着 Programmable AI Team OS 的方向持续进化。
